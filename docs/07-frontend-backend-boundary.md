
# 前后端边界文档：双人变美变瘦大作战

# 1. 文档目的

本文档用于说明当前项目未来从 **纯前端 Web MVP** 演进到 **前后端分离 / 多设备同步 / 数据库持久化** 时，各层应该负责什么。

它重点回答：

```text
前端负责什么？
后端负责什么？
数据库负责什么？
API 如何连接前后端？
哪些计算可以前端预览？
哪些结果必须由后端最终确认？
```

核心原则：

> 前端可以预览，但最终结果必须由后端重新计算和确认。
> 前端不能直接连接数据库。
> 前端不能决定最终钱包余额。
> 后端不能相信前端传来的宝石、金币、钱包结果。

---

# 2. 当前阶段与未来阶段

## 2.1 当前阶段：Web MVP

当前项目主要是前端 Web 应用，数据通过本地存储保存。项目中已经有 `AppDataStore` 抽象，当前实现是 `localStorage`。`AppDataStore` 定义了 `load / save / clear`，并通过 `AppDataSnapshot` 保存运行数据和配置数据。

当前本地存储实现位于 `local-storage-app-data-store.ts`，它通过 `window.localStorage` 读取和保存数据，并在服务端环境下避免访问浏览器 API。

## 2.2 未来阶段：前后端分离

未来接入后端后，架构应演进为：

```text
前端 UI
  ↓
API Client
  ↓
后端 API
  ↓
业务服务层
  ↓
数据库
```

当前的 `AppDataStore` 可以作为未来替换数据来源的关键抽象：

```text
createLocalStorageAppDataStore()
  ↓
createRemoteAppDataStore()
```

也就是说，未来优先替换 Store 层，而不是让所有 UI 组件直接改为调用数据库或 API。

# 3. 总体边界原则

## 3.1 前端职责

前端负责：

```text
页面展示
表单输入
交互反馈
本地 UI 状态
奖励预览
调用 API
展示后端返回结果
移动端适配
toast 提示
弹窗打开关闭
```

前端可以做“预览计算”，例如用户输入热量缺口和运动分钟后，前端即时展示预计获得多少宝石和金币。

但前端预览结果只是体验优化，不是最终事实。

---

## 3.2 后端职责

后端负责：

```text
登录校验
权限判断
数据校验
最终奖励结算
钱包一致性
数据库写入
事务处理
错误返回
数据导入导出校验
多设备同步冲突处理
```

后端必须重新计算宝石、金币、bonus、钱包余额等关键结果。

后端不能直接信任前端传来的：

```text
fishGems
catGems
bonusGems
coinDelta
wallet.gems
wallet.coins
weekGemTotal
```

这些都必须由后端根据原始输入和规则重新计算。

---

## 3.3 数据库职责

数据库负责长期保存事实数据和配置数据。

数据库保存：

```text
用户账号
情侣空间
每日记录
兑换记录
钱包流水
奖励分类
用户配置
规则配置
数据版本
```

数据库不负责：

```text
UI 弹窗状态
toast
当前 tab
输入框未保存草稿
hover 状态
动画状态
```

---

## 3.4 API 职责

API 是前端和后端之间的边界。

API 负责：

```text
接收前端请求
校验参数
调用后端业务服务
返回标准响应
返回错误码
隐藏数据库细节
```

前端只调用 API，不直接访问数据库。

---

# 4. 前端负责什么

## 4.1 页面展示

前端负责展示：

```text
首页成长面板
记录今天弹窗
成长地图
成长日志
记录详情
兑换商店
兑换记录
设置页，未来
登录页，未来
```

前端应只展示后端或本地状态提供的数据，不应自行伪造最终结果。

---

## 4.2 表单输入

前端负责收集用户输入，例如：

```text
体重
热量缺口
运动分钟
记录日期
兑换备注
兑换时间
奖励类别名称
奖励价格
```

前端可以做基础校验：

```text
必填校验
数字格式校验
非负数校验
未来日期禁用
输入框空值处理
```

但最终校验必须由后端执行。

---

## 4.3 交互反馈

前端负责：

```text
弹窗打开关闭
按钮禁用
loading 状态
toast 提示
错误提示展示
空状态展示
移动端布局
```

例如：

```text
保存中
保存成功
资源不足
日期不合法
网络错误
```

---

## 4.4 前端预览计算

前端可以预览：

```text
预计鱼鱼宝石
预计猫猫宝石
预计双人 bonus
预计金币变化
预计热力图颜色
兑换是否资源足够
```

预览的作用是让用户及时看到反馈。

但是：

```text
前端预览 ≠ 最终结算
```

保存时后端必须重新计算。

---

## 4.5 前端不应该做什么

前端不应该：

```text
直接连接数据库
直接决定最终钱包余额
直接相信本地计算作为最终结果
直接写入核心业务数据到数据库
绕过 API 修改记录
绕过后端权限校验
保存未校验的奖励结果
```

---

# 5. 后端负责什么

## 5.1 身份认证

后端负责：

```text
用户登录状态
用户身份识别
token 校验
会话管理
```

未来如果支持情侣空间，后端必须知道：

```text
当前用户是谁
属于哪个 CoupleSpace
能否访问该空间数据
```

---

## 5.2 权限判断

后端负责判断：

```text
用户是否属于该情侣空间
用户是否可以查看记录
用户是否可以编辑记录
用户是否可以删除记录
用户是否可以兑换奖励
用户是否可以管理奖励分类
```

前端传来的 `spaceId`、`recordId` 不能直接信任。

---

## 5.3 数据校验

后端必须校验：

```text
日期是否合法
是否未来日期
体重是否合法
热量缺口是否合法
运动分钟是否合法
兑换价格是否合法
奖励类别是否存在
资源是否足够
记录是否属于当前空间
```

---

## 5.4 最终结算

后端负责最终计算：

```text
鱼鱼宝石
猫猫宝石
双人 bonus
金币变化
热力图状态
钱包变化
连续天数
本周统计
```

当前前端代码里已经有每日记录服务会根据输入生成完整 DailyRecord，并计算宝石、金币、bonus、热力图等派生状态。未来后端应承担这类最终结算职责。`daily-record-service.ts` 中创建记录时会调用宝石、金币、bonus 和热力图规则，并在变更后重建派生状态。

---

## 5.5 钱包一致性

后端必须保证钱包一致。

后端不能直接使用前端传来的钱包余额。

正确做法：

```text
后端读取当前记录和钱包流水
后端重新计算本次变化
后端在事务中写入记录和资源变动
后端返回新的钱包状态
```

未来推荐引入 `WalletLedger`，用流水保证资源变化可追踪。

---

## 5.6 事务处理

这些操作必须使用事务：

```text
新增每日记录 + 更新钱包
编辑每日记录 + 回算钱包
删除每日记录 + 回算钱包
兑换奖励 + 扣除钱包 + 新增兑换记录
删除兑换记录 + 回退资源
```

如果其中一步失败，必须整体回滚。

---

## 5.7 错误返回

后端应返回结构化错误，例如：

```text
INVALID_DATE
FUTURE_DATE_NOT_ALLOWED
RECORD_NOT_FOUND
PERMISSION_DENIED
INSUFFICIENT_BALANCE
VALIDATION_FAILED
CONFLICT
SERVER_ERROR
```

前端根据错误码展示温和提示。

---

# 6. 数据库负责什么

## 6.1 长期保存事实数据

数据库保存用户真实产生的数据：

```text
每日记录
兑换记录
钱包流水
用户配置
奖励分类
情侣空间
用户账号
```

---

## 6.2 数据库不负责业务解释

数据库不应该写复杂业务规则。

例如数据库不直接决定：

```text
今天该得多少宝石
是否触发金币
是否点亮热力图
```

这些由后端服务层计算。

---

## 6.3 推荐数据库对象

未来可设计：

```text
users
couple_spaces
partner_profiles
daily_records
exchange_records
exchange_categories
user_configs
wallet_ledgers
```

---

## 6.4 数据库应保存原始输入

对于每日记录，数据库优先保存事实数据：

```text
recordDate
fishWeightKg
fishDeficit
fishMinutes
catWeightKg
catDeficit
catMinutes
createdAt
updatedAt
```

派生结果可以保存快照，但不应替代原始输入。

# 7. API 如何连接前后端

## 7.1 API 基本原则

API 是唯一通信入口：

```text
前端 → API → 后端服务 → 数据库
```

不允许：

```text
前端 → 数据库
```

---

## 7.2 API 请求应该传什么

前端应传原始输入，而不是最终结算结果。

例如创建每日记录时，前端应该传：

```json
{
  "recordDate": "2026-05-14",
  "fish": {
    "weightKg": 70.5,
    "deficit": 317,
    "minutes": 0
  },
  "cat": {
    "weightKg": 60.2,
    "deficit": 244,
    "minutes": 0
  }
}
```

不应该传：

```json
{
  "fishGems": 3,
  "catGems": 3,
  "bonus": 0,
  "coins": 2,
  "wallet": {
    "gems": 49,
    "coins": 4
  }
}
```

这些由后端计算。

---

## 7.3 API 响应应该返回什么

后端保存成功后返回完整确认结果：

```json
{
  "record": {
    "id": "daily-xxx",
    "recordDate": "2026-05-14",
    "fish": {
      "weightKg": 70.5,
      "deficit": 317,
      "minutes": 0,
      "gems": 3
    },
    "cat": {
      "weightKg": 60.2,
      "deficit": 244,
      "minutes": 0,
      "gems": 3
    },
    "bonus": 0,
    "coins": 2
  },
  "wallet": {
    "gems": 49,
    "coins": 4
  },
  "stats": {
    "weekGemTotal": 30,
    "weekCoinTotal": 2
  }
}
```

前端用后端返回值刷新页面。

# 11. 钱包一致性原则

## 11.1 不推荐直接存最终余额作为唯一事实

钱包余额容易因为编辑历史记录、删除记录、删除兑换记录而变化。

因此未来应考虑：

```text
wallet_ledger 作为资源变化流水
wallet balance 作为快照
```

## 11.2 推荐逻辑

```text
每日记录产生资源 → 写入 ledger 正数
兑换奖励消耗资源 → 写入 ledger 负数
编辑记录 → 反向冲销旧流水，再写入新流水
删除记录 → 删除或冲销相关流水
钱包余额 → 根据 ledger 汇总或更新快照
```

# 12. 前端与后端的共享规则

## 12.1 可共享

这些可以前后端共享：

```text
TypeScript 类型
宝石规则
金币规则
热力图规则
输入校验 schema
资源格式定义
```

如果未来前后端都使用 TypeScript，可以把规则放到共享包中。

---

## 12.2 必须以后端为准

即使前后端共享规则，也必须以后端结算为准。

原因：

```text
前端代码可以被篡改
前端 localStorage 可以被改
前端传参不可信
多设备可能产生冲突
```

# 13. 错误处理边界

## 13.1 后端返回错误码

后端返回：

```json
{
  "error": {
    "code": "INSUFFICIENT_BALANCE",
    "message": "资源不够"
  }
}
```

## 13.2 前端负责展示友好提示

前端将错误转成温和文案：

```text
还差一点点，攒够再来换吧
只能记到今天哦
这条记录没有找到
网络有点慢，稍后再试
```

# 14. 离线与同步边界，未来

## 14.1 当前 MVP

当前是本地存储，无后端同步。

## 14.2 未来多设备同步

可选方案：

```text
在线优先：所有写操作走 API
离线缓存：本地暂存，恢复网络后同步
冲突解决：以后端版本号为准
```

## 14.3 冲突处理

典型冲突：

```text
两台设备同时编辑同一天记录
一台设备删除记录，另一台设备修改记录
兑换记录同时编辑
```

未来可引入：

```text
updatedAt
version
operation log
last write wins
手动合并
```

# 15. 安全边界

## 15.1 前端不可信

前端传来的所有数据都必须重新校验。

包括：

```text
用户 ID
空间 ID
记录 ID
宝石金币结果
钱包余额
兑换价格
奖励类别
```

---

## 15.2 后端必须校验权限

用户只能访问：

```text
自己的数据
所在情侣空间的数据
被授权的记录和配置
```

---

## 15.3 数据库不暴露给前端

数据库连接信息、查询逻辑、权限逻辑都必须在后端。

当前可作为纯前端 Next.js 应用运行，数据在浏览器本地。

未来部署应分为：

```text
前端应用

对象存储，可选
认证服务，可选
```

## 16.3 推荐边界

```text
浏览器
  ↓ HTTPS
Next.js / 前端页面
  ↓ API
后端服务
  ↓ ORM / SQL
数据库
```

---

# 17. 总结

前后端边界的核心原则是：

```text
前端负责体验
后端负责可信
数据库负责长期保存
API 负责连接和隔离
```

最重要的规则：

```text
前端可以预览，但后端必须重新计算。
前端不能直接连接数据库。
前端不能决定最终钱包余额。
后端不能相信前端传来的宝石金币结果。
数据库只保存事实数据和配置，不保存临时 UI 状态。
```

未来只要守住这个边界，项目就可以从当前 Web MVP 平滑演进到后端、多设备、小程序或 App。
